Issue #16's "embed password change and 2FA screens fully in the app" asked for more than borrowed colours: these screens should carry the *same* persistent header and tab bar as every other mobile screen, reachable by a boosted (AJAX) navigation from mobile/me.html rather than a full page reload. This duplicates mobile/base.html's header/tab-bar markup rather than {% extends "mobile/base.html" %}-ing it -- a real attempt at that hit a genuine Django limitation: base.html's own {% block content %} and allauth's own {% block content %} (nested inside allauth/layouts/base.html's {% block main %}, which is what base_template actually needs to expose) share the same block *name* across one {% extends %} chain, and Django resolves a block name to whichever template in the whole chain is most derived, full stop -- regardless of which ancestor "meant" it for something else, and regardless of nesting depth. Since login.html's own {% block content %} doesn't call {{ block.super }}, it wins outright and silently discards everything base.html's content slot and this file would otherwise have contributed, including the {% block main %} anchor allauth needs to fill. Same reasoning management/_auth_base.html and controlpanel/_auth_base.html already settled on for their own skins -- a standalone shell, not a real {% extends %} of the app's own base, is the only sound way to share chrome with an allauth screen. Keep this file's header/tab-bar in sync with mobile/base.html's own by hand. {% block main %} is the contract templates/allauth/layouts/base.html and this file's own siblings target (head_title, extra_head, main, extra_body).
